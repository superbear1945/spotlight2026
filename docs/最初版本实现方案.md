卡牌玩法与数据驱动架构实施方案

## 1. 目标与已确认规则

在现有 Unity 2022.3、URP 2D 工程中实现 Windows 桌面可玩版本，以玩法验证为优先，使用中文界面和简洁占位素材。

以 [玩法.md](玩法.md) 为基础，并遵守仓库根目录的 [AGENTS.md](../AGENTS.md)，同时更新文档以落实本次确认：

- **彻底移除反击**，删除对应开关、结算、AI 判断及相关描述。
- **只支持上下左右移动和互换**，删除斜移配置。
- 传送组件只实现星门的四邻部署扩展。
- Boss 对可击杀特殊卡执行优先击杀；其余特殊卡排在资源卡之后。
- 正式数值来自 Excel 编译产物；调试覆盖仅存在于当前运行会话。
- 静态 UI 使用 UXML，动态手牌及棋盘使用 UGUI。

其余玩法与默认数值按文档实现，包括六种玩家卡、Boss、覆盖升级、资源结算、墓地洗回、弃牌阶段、家移动和手动 Boss 模式。

## 2. 类、组件与运行状态

采用单一 `Card : MonoBehaviour`，具体卡种不建立子类。项目自定义继承链不超过三层，不计 Unity 自身的框架继承；当前设计不需要申请例外。

| 类型 | 职责 |
|---|---|
| `Card` | 持有组件引用，绑定卡牌或单位身份，协调显示 |
| `CombatComponent` | 持有战斗配置 SO，提供生命、攻击、射程、移动属性及对应状态入口 |
| `ResourceComponent` | 持有资源配置 SO，提供产出、维持费和支付状态入口 |
| `TeleportComponent` | 持有传送配置 SO，提供星门部署扩展能力 |
| `GameSession` | 唯一对局状态及命令入口，协调回合、规则、AI 和胜负 |
| `CardRecord` | 仅保存卡牌 ID、卡种 ID、阵营，在牌库、手牌、墓地间流转 |
| `UnitState` | 保存在场单位 ID、来源卡牌 ID、位置、当前生命、行动状态和部署顺序 |
| `HomeState` | 独立的家状态，参与占位、受击和移动，不进入牌库 |

组合与数据约束：

- 当前所有普通单位均有战斗组件，以支持生命和移动；资源组件用于产出或维持费；传送组件按配置添加。
- 卡种分类独立保存，不能通过是否具有战斗组件推断“攻击卡”。
- 覆盖升级、部署限制、互换、寻路和 AI 使用普通 C# 规则服务，不新增卡牌能力组件。
- 共享 SO 只保存基础配置；当前生命、位置、行动机会等只保存在本局状态中。
- SO 实现只读配置接口，规则内核依赖接口；测试可使用普通 C# 配置对象，无需创建场景。
- 不建立第二套同名纯 C# 能力组件，也不在 MonoBehaviour 中重复保存战斗状态。

最小公共入口：

- `GameSession.Execute(command)`：部署、移动、攻击、互换、弃牌、结束回合。
- `GameSession.GetLegalActions(selection)`：提供合法目标与高亮依据。
- `GameSession.GetSnapshot()`：提供 UI、日志及调试快照。
- 命令结果包含成功状态、失败原因和有序事件；玩家与 AI 共用规则入口，动画不决定结算结果。

程序集按规则内核、Unity 运行层、编辑器工具和测试划分，保持单向依赖。

## 3. Excel 配置与编译工具

采用已选择的路线：

**Excel → 强类型表结构校验 → 卡种及组件 SO → 每卡种 Prefab → 配置目录。**

使用仅限编辑器的 [ExcelDataReader](https://github.com/ExcelDataReader/ExcelDataReader/releases) 读取 `.xlsx`，固定依赖版本。正式运行包不包含 Excel 解析器。

表格按职责拆分为卡种、卡组、对局规则、家、Boss 兵位及表现参数。每张表由明确的 C# 行类型约束，卡种表每行生成一个 Prefab；其他表生成相应 SO。

- 卡种行包含稳定 ID、名称、分类、三个组件的配置、组件启用信息、升级目标和部署限制。
- 每卡种一个定义资产，组件 SO 作为子资产集中保存；Prefab 保存组件组合及 SO 引用，不重复存储数值。
- 默认卡牌属性、棋盘尺寸、抽牌数量、维持费、补兵间隔等从 Excel 提供。动画时间等可调参数集中配置；规则代码不按具体卡名分支。
- 外观模板与生成资产分离，避免重编译覆盖手工制作的外观。

编译器必须检查：

- 未定义列、重复表头、缺失必需列、有数据但无表头的列，以及未声明的数据表。
- 公式、错误单元格、合并数据单元格、非法类型和数值范围。
- 重复 ID、空名称、去除首尾空格后的重名、非法分类。
- 卡组、Boss 卡种和升级目标引用；升级不能指向自身或非资源卡。
- 组件开关与字段是否匹配，以及 AI 模式的 Boss 卡种是否合法。

正式数据区域拒绝公式；辅助计算与正式导入区域分离。错误报告一次汇总，并定位到文件、工作表、行、列和原因。

生成保护：

- 全部验证通过后才发布；失败保留上一套有效产物，发布异常可回滚。
- 使用稳定 ID 更新已有资产，保留 GUID；改显示名称不破坏关联。
- 生成 SO、Prefab 配置使用只读 Inspector，提示源表位置。
- 进入 Play 和构建前校验源文件摘要、生成配置及 Prefab 组合；过期、缺失或手工篡改时阻止运行或构建。
- 提供“验证配置”“编译全部配置”入口、默认工作簿及策划填写说明。

## 4. 玩法、UI 与调试流程

对局初始化由单一 Bootstrap 明确执行：加载有效配置、创建对局、绑定 UI，再按先手顺序进入回合。

核心结算顺序：

- 玩家回合：恢复行动 → 按开关清零资源 → 结算家和单位产出 → 按部署顺序支付维持费 → 抽牌 → 玩家操作。
- 玩家结束回合：超限时先进入弃牌阶段，完成后才进入 Boss 回合。
- Boss 回合：恢复行动 → 首次部署或到期补兵 → 按部署顺序行动 → 自动结束；手动模式改由玩家提交操作。
- 每次行动完成后检查胜负，对局结束立即停止后续 AI 行动与补兵。

实现时固定以下边界：

- 回合编号从 1 开始，双方各完成一次行动回合后递增；补兵到期为阵亡回合加配置间隔。
- Boss 首次成功部署可立即行动，死亡补回遵守召唤失调；无空位持续等待。
- BFS 寻路固定按上、右、下、左处理并列路径。移动后不能追加攻击。
- 部署、升级和死亡保持卡牌记录守恒；重新部署创建满血新单位，在场单位跨回合保留伤势。
- 星门扩展随位置变化，刚部署即可生效，欠费不关闭扩展，离场立即失效。
- 家使用固定己方区域，区域不随家移动；保留文档中的遮挡、无空位不判负等规则。

UI：

- UXML/USS：资源与回合信息、按钮、日志、单位详情、调试面板及胜负界面。
- UGUI：手牌、棋盘格、卡牌实例及合法目标高亮。
- 保留点击选牌、点击目标的完整操作链；首版不要求拖拽、复杂抽卡演出或正式卡面。
- 引入 DOTween Free，仅实现必要的选中、出牌、移动和受击反馈；重开、销毁和对象复用时清理动画。
- 使用统一输入入口，防止 UXML 面板点击穿透至 UGUI；模态面板和弃牌阶段由规则层共同限制操作。

调试：

- 仅在编辑器或 Development Build 提供调试入口。
- 保留配置草稿、临时新增卡种、JSON 导入导出及“应用并重开”；修改作用于内存中的配置克隆。
- 应用前完整验证并创建候选对局，成功后替换；失败保留原对局和草稿。
- 同一次运行中保留调试草稿；退出 Play 或重启程序后清空，重新读取 Excel 产物。
- JSON 兼容仅覆盖文档明确列出的旧格式；旧反击、斜移字段迁移时移除并提示，不恢复废弃功能。

## 5. 测试方案与 GitHub Actions PR 流程

### 5.1 测试基础与分层

当前已有 `Assets/Spotlight/Tests/EditMode/GameSessionTests.cs` 和 `Spotlight.Tests.EditMode` 测试程序集，使用 Unity Test Framework；尚未建立 `.github/workflows`。以下是需要随开发落实的测试要求，已有测试文件不代表本节覆盖项已全部实现或运行通过。

规则、配置校验、寻路和 AI 决策保留为普通 C# 逻辑，通过配置接口和可注入的随机源测试；MonoBehaviour 只承担组件绑定、生命周期和表现。测试主要通过公开命令和快照断言，不通过反射改写私有状态，不为测试复制一套玩法实现。

| 层级 | 建议位置 | 主要验证内容 | 执行方式 |
|---|---|---|---|
| 规则单元与对局集成 | `Assets/Spotlight/Tests/EditMode/` | 规则服务、合法动作、命令结果、事件顺序、跨回合状态、AI 决策 | Unity EditMode，无需玩法场景 |
| 配置编译与资产集成 | `Assets/Spotlight/Tests/Editor/` | 真实 `.xlsx` 读取、完整校验、SO/Prefab 生成、GUID 和发布回滚 | Unity EditMode，独立编辑器测试程序集 |
| 运行与 UI 集成 | `Assets/Spotlight/Tests/PlayMode/` | Bootstrap、Card 绑定、输入路由、调试重开、动画与对象销毁 | Unity PlayMode，使用最小测试场景 |
| Windows 构建冒烟 | `ci/` 下的运行脚本与专用验收夹具 | 正式配置加载、启动、按固定命令完成对局、正常退出、运行日志 | GitHub Actions 的 Windows 环境 |
| 人工交互验收 | `docs/测试说明.md` 中的检查表 | 中文字体、分辨率适配、点击反馈、动画观感、完整手动对局 | 记录被测提交、构建产物及结果 |

新增测试程序集保持单向依赖，编辑器测试可引用编译器与运行层，运行层不得引用测试程序集；测试代码和夹具不进入正式包。程序集划分随对应模块交付，不建立只有名称而无有效用例的测试套件。

### 5.2 必须覆盖的行为矩阵

每项至少包含正常行为、非法输入或失败行为、边界条件；涉及状态修改时还需验证失败后状态不变。新增玩法或配置字段必须扩展相应矩阵，不能只验证“没有抛异常”。

| 测试领域 | 必须保留的回归用例与断言 |
|---|---|
| 命令与权限 | 非当前阵营、模态阻塞、弃牌阶段、已结束对局的非法命令被拒绝；拒绝后完整规则快照不变且无成功结算事件；合法目标与实际命令接受结果一致 |
| 棋盘、移动与攻击 | 四邻移动和互换；拒绝斜向移动步骤与斜向互换，但允许合法路径到达斜向位置；边缘、阻挡、无路、距离临界值、BFS 并列路径顺序；互换消耗双方行动，移动后不能攻击；射程与遮挡开关、攻击不触发反击 |
| 卡牌生命周期 | 部署、覆盖升级、死亡、弃牌和抽牌中途洗回；玩家卡牌 ID 在牌库、手牌、墓地和在场来源间唯一且总数守恒；升级回收旧卡，重新部署满血，同卡种状态独立，跨回合保留伤势 |
| 资源与回合 | 双方先手、左右镜像、回合编号；清零或累积、产出先于维持费、按部署顺序支付、余额刚好与不足；行动恢复、召唤失调、手牌上限临界值与强制弃牌完成后才切换阵营 |
| 家与星门 | 家只能在固定己方区域移动且每回合一次；无空位不判负；星门刚部署生效、欠费保持、移动后更新、离场失效，同类相邻与部署区域限制 |
| Boss AI 与补兵 | 可击杀特殊卡优先，其余特殊卡排在资源卡后；并列选择可复现；首次成功部署立即行动、补兵遵守召唤失调、死亡回合加间隔计时、堵位等待后恢复；自动与手动模式权限；胜负后立即停止行动和补兵 |
| Excel 输入校验 | 未声明表或列、重复表头、缺列、无表头数据列、公式、错误和合并单元格、类型与范围、重复 ID、空名称及去空格重名、非法分类和引用、升级自指或非资源目标、组件字段冲突、非法 Boss 卡种；一次报告多项错误并准确定位 |
| 生成与发布 | 同源重复编译产物语义一致且无无意义差异、改名保留 GUID 与引用；校验失败不改旧产物，发布中途故障注入后完整回滚；缺失、过期、手改 SO/Prefab 能被运行及构建检查拒绝；手工外观不被覆盖 |
| 调试与数据隔离 | 候选对局验证成功才替换，失败保留原对局与草稿；JSON 支持格式和非法格式、旧字段移除提示；重开保留草稿，结束运行后恢复正式配置，源 Excel 和生成资产不变 |
| Unity 与 UI | Bootstrap 只初始化一次、组件和 SO 引用匹配；点击选牌到提交命令的完整链路；**棋盘卡牌的点击必须穿过卡牌落到格子上（卡牌关闭射线检测），点击棋子的射线命中格而非卡牌**；**棋盘快照变化后每张卡牌都挂在对应格子且偏移归零，移动动画结束或被中断后都不会把棋子留在旧格**；UXML 点击不穿透 UGUI，弃牌与模态限制同时生效；重开、销毁、复用无遗留监听、重复命令或动画回调；非开发构建无调试入口 |

夹具使用独立的最小配置，另保留一套正式默认工作簿的端到端编译与启动测试。资产测试在隔离的临时目录创建和清理文件，禁止改写生产资产；涉及静态状态、场景、事件和动画的用例必须在结束时恢复环境。

随机测试固定种子，失败报告附种子、配置摘要和命令序列；对多组种子执行有步数上限的合法命令序列，每步检查卡牌守恒、格子占用唯一、资源合法与胜负后状态稳定。异步测试等待明确事件或状态并设置超时，不以固定延时或执行顺序掩盖竞态。

### 5.3 PR 自动检查流程

新增 `.github/workflows/pr-checks.yml`，以 `pull_request` 为主要入口，覆盖创建、更新提交及重新打开；同时提供 `workflow_dispatch` 复现入口，并在默认分支 `push` 后执行回归。每次检查记录实际检出的提交 SHA；PR 检查以与目标分支合并后的待测代码为准。

1. **准备环境**：从 `ProjectSettings/ProjectVersion.txt` 读取并核验 Unity 精确版本；当前为 `2022.3.62f3c1`。先验证所选 runner 的编辑器安装、授权和 Windows 构建模块可用，不擅自替换为其他版本；若托管环境无法提供该版本，使用预装相同版本的隔离 Windows runner。包版本由 `Packages/manifest.json`、锁文件和固定的 Git 依赖提交共同约束。
2. **文档与代码规范检查**：校验 Markdown 本地相对链接、C# 格式及命名规则、公共 API 与新增类/函数的 XML 注释结构。使用项目内固定版本的检查工具；注释是否解释设计理由、文档是否符合实际行为仍由代码审查确认。规范检查失败应指出文件、行号和违反的约束。
3. **EditMode 测试**：运行规则、配置及资产测试程序集，检查编译错误、测试结果与 Editor 日志。配置编译测试必须使用真实工作簿和临时资产，不能只测试手工创建的行对象。项目必需测试程序集必须被发现且包含实际执行的用例。
4. **PlayMode 测试**：运行生命周期、UI 输入及调试集成用例。与 EditMode 使用独立检出目录、独立结果目录；不得让多个 Unity 进程同时打开同一工程。UI 测试环境须具备所需图形能力。
5. **Windows 构建与冒烟**：测试通过后，从源工作簿编译配置并执行构建前检查，生成 Windows 非 Development 包，验证启动与正式配置加载、无调试入口、日志无未处理异常。固定命令完成对局的自动冒烟使用单独的验收构建入口；正式包不得包含测试驱动入口。正式包的完整人工交互验收在发布前补齐。
6. **结果归档与合并检查**：无论成功或失败均上传已生成的测试 XML、Editor/Player 日志、构建日志和失败截图；结果按提交及测试阶段区分，保留 14 天。汇总任务 `PR Validation` 始终运行，只有所有必需任务成功且结果文件有效时才成功；将该检查设置为目标分支的必需状态检查。

Unity 测试命令采用 `-batchmode -runTests -projectPath … -testPlatform EditMode|PlayMode -testResults … -logFile …`，两种模式分别启动；不额外添加会使测试提前退出的 `-quit`。以项目所用 [Unity Test Framework 1.1 命令行文档](https://docs.unity.cn/Packages/com.unity.test-framework%401.1/manual/reference-command-line.html) 为依据，同时核验进程退出码、XML 中的失败项与实际执行数量，不能仅凭进程退出就判定通过。

工作流还需落实：

- 对同一 PR 的旧提交取消过时运行；各任务设置超时，异常退出或授权失败必须报告失败，不转成测试成功。
- 首版所有 PR 执行完整必需流程，不对必需 workflow 使用路径过滤；以后若为纯文档变更优化，汇总任务必须显式校验跳过理由，不能把缺失结果当作成功。GitHub 对 [跳过的 job](https://docs.github.com/en/pull-requests/reference/status-checks) 和 [路径过滤跳过的 workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) 有不同的状态处理。
- 缓存仅用于加速，键包含操作系统、Unity 版本、目标平台与依赖锁文件摘要；缓存缺失时仍能完整执行，不缓存测试结论。Unity 版本或包升级时执行一次无缓存验证。
- 工作流默认仅授予读取仓库权限，第三方 Action 固定到审核过的提交 SHA。Unity 授权使用 runner 的合规授权方案，凭据不得写入仓库或日志。
- Fork PR 默认无法取得仓库 secrets，授权不可用时明确标记检查受阻；外部贡献需经审查后在隔离且已授权的环境运行同一待合并提交，测试结果回传对应检查。不得用 `pull_request_target` 携带凭据执行未经信任的 PR 代码，遵循 [GitHub 的事件权限说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)；此路径须在开放外部贡献前验证可用。

### 5.4 扩展、缺陷修复与测试验收

- 每个功能 PR 同步提交对应测试；缺陷修复先建立能复现问题的失败用例，再验证修复后通过。新增卡种、组件配置或规则开关时，同时覆盖启用、禁用、非法配置及与现有规则的交互。
- 对规则内核和编译校验代码建立行与分支覆盖率报告，接入经版本兼容性验证的覆盖率工具后，将首轮完整回归结果记录为基线；后续 PR 不得降低已设定基线。阈值及排除目录写入仓库配置，不能通过排除业务代码提升数字。覆盖率不能替代本节行为矩阵。
- 不允许通过删断言、无说明忽略测试或自动重跑直到成功来合并。偶发失败应记录种子、日志和复现步骤并修复；必需测试缺失、全被跳过、结果损坏或超时均阻止合并。
- 在 `docs/测试说明.md` 记录本地 Test Runner 操作、与 CI 一致的命令、环境与授权前提、夹具位置、测试编号与需求映射、报告下载和失败排查；人工验收记录被测 SHA、操作步骤、预期与实际结果。
- CI 接入完成的判据：真实 PR 成功运行全部必需阶段；临时引入失败用例时能够阻止合并并提供日志，修复后恢复通过。工作流文件存在、本地通过或人工验收均不能代替 GitHub Actions 上的实际 PR 验证。

## 6. 文档、注释与代码风格约束

本节落实根目录 [AGENTS.md](../AGENTS.md) 的四项要求，并补充本方案的文档交付约定。以下要求同样适用于业务代码、编辑器工具、测试类、测试辅助函数及 CI 脚本；自动生成代码的相应规范应由生成模板保证。

### 6.1 命名与代码组织

- **所有私有字段**使用 `_` 前缀加小驼峰，例如 `_currentHealth`、`_configuration`；包括静态字段、只读字段及带 `[SerializeField]` 的字段，不因序列化或可见性需求省略前缀。
- **类名和函数名**使用大驼峰（PascalCase），例如 `GameSession`、`Execute`、`ValidateWorkbook`；局部变量和参数等普通变量使用小驼峰（camelCase），例如 `targetCell`、`cardId`。补充统一约定：属性、事件和枚举类型及成员使用 PascalCase，接口使用 `I` 前缀。
- 缩写、测试数据和辅助代码也要可读，避免用 `g`、`d` 等无语义名称代替 `gameSession`、`configuration`；测试函数名描述条件与预期行为，例如 `Execute_WhenTargetIsOccupied_RejectsWithoutChangingState`。
- C# 使用四空格缩进、独立行大括号，避免将整段测试或多个操作压在一行。通过 `.editorconfig` 和固定版本的检查工具统一执行，不依赖个人 IDE 设置。
- 修改序列化字段名称时同步评估资产迁移，必要时使用字段迁移标记并补资产加载回归测试；不得仅为满足命名规则造成已有场景、Prefab 或数据兼容性丢失。

### 6.2 类与函数注释

每个新增类和函数都必须有详细中文说明，回答“作用是什么、输入是什么、输出是什么、为什么需要它”；私有辅助函数、构造函数及测试函数同样适用。

- 类使用 XML 文档注释：`<summary>` 说明职责，`<remarks>` 说明依赖或输入来源、对外提供的结果及存在理由，并标明状态归属和生命周期约束。
- 函数使用 `<summary>` 说明行为，逐项用 `<param>` 说明参数含义、单位、范围及可空性；有返回值时用 `<returns>` 描述结果与失败含义，用 `<remarks>` 解释必要性、状态修改和副作用。确有异常契约时补充 `<exception>`。
- 无参数、无返回值和构造函数不编造参数或返回标签，在说明中明确“无显式输入”“无返回值，更新何种状态”或“创建何种对象”。测试函数说明夹具前提、触发操作、预期断言和防止哪类回归。
- 注释重点解释结算顺序、边界、不变量和设计原因，不以复述函数名充数；实现变更时同步修改注释。废弃反击、斜移相关旧逻辑时一并更新注释，迁移说明可保留历史字段名称。

### 6.3 文档同步与 PR 交付

- 仓库文档使用 UTF-8、清晰标题、稳定术语和仓库相对链接，避免将个人磁盘路径写入团队文档。玩法规则以 `docs/玩法.md` 为准；本方案维护实现设计；`docs/实施进度.md` 区分待实施、实施中和已验证，不把计划写成完成事实。
- 规则、公开接口、配置字段或工具操作变化时，同一 PR 更新关联文档；说明默认值、有效范围、错误处理及兼容或迁移影响。策划填写说明包含有效与无效工作簿示例，操作文档包含执行前提和可验证结果。
- 设计取舍记录选择原因、依赖和限制；架构图及流程图随实现更新。机器生成文档注明来源和重生成方式，避免直接手改生成产物。
- PR 描述列出具体行为变化、关联需求、测试用例和 GitHub Actions 结果、文档更新及未覆盖项。开发交付必须同时包含可执行测试，并接入第 5 节的 PR 流程；不能仅提交一段人工测试说明替代测试用例。
- 审查清单至少检查：私有字段前缀、函数与类命名、新增类/函数的完整注释、文档与实现一致、回归测试覆盖、必需 PR 检查通过。自动检查负责可机械验证的规则，评审负责注释质量和测试是否真正证明行为。

## 7. 实施顺序、架构图与验收

按以下顺序交付：

1. 更新玩法约定，建立类职责、配置接口、默认 Excel 与文档和代码规范；先打通 Unity 精确版本、授权、有效 EditMode 用例及 GitHub Actions PR 检查，确认失败能阻止合并。
2. 完成校验编译器、只读 SO、生成 Prefab 及运行／构建检查，同步交付工作簿、资产发布与回滚测试。
3. 完成规则内核和 Boss AI，补齐行为矩阵中的 EditMode 回归测试及覆盖率基线。
4. 接入 UXML、UGUI、调试面板和必要反馈，同步加入 PlayMode 测试及必需 PR 检查。
5. 接入 Windows 构建与冒烟检查，完成正式包人工验收、测试说明、策划操作说明及架构图。全部阶段接入后，第 5 节完整 PR 流程必须通过，才能验收首版。

使用 `fireworks-tech-graph` 技能（执行时从当前环境的技能目录读取说明），按最终实现生成四组视图：

- 模块架构与程序集依赖。
- Card 类、三个组件、SO 和运行状态的关系。
- Excel 编译、配置加载、会话调试及 UI 数据流。
- 玩家回合、弃牌、Boss 部署补兵和胜负流程。

图纸采用默认 Flat Icon 风格，交付 SVG、PNG 和可缩放离线 HTML；执行结构、布局检查并查看 PNG，验证中文、连线和标签完整。

验收重点：

- **配置**：未知列、公式、重复 ID、非法引用会阻止编译；失败不破坏旧资产；重复编译稳定；改名保留引用；手改生成数值会被检查发现。
- **玩法**：移动、攻击、遮挡、升级、互换、资源欠费、抽牌中途洗回、强制弃牌、双方先手、左右镜像、Boss 堵位和补兵计时均符合规则。
- **数据隔离**：同卡种单位互不影响；死亡再部署恢复初始生命；牌库不复制场上卡；调试不改变源资产，下一次运行恢复正式配置。
- **UI 与构建**：中文显示完整，点击不穿透，手动与 AI 模式权限正确，Windows 非开发构建可完成一局且无调试入口。
- **架构**：仅三种卡牌能力组件，无具体卡种子类，无超过三层的项目自定义继承链，无反击或斜移功能残留。
- **测试与 CI**：行为矩阵有对应可执行用例；真实 PR 上规范、EditMode、PlayMode、Windows 构建及冒烟检查通过；失败可阻止合并，日志和结果可下载，本地可按测试说明复现。
- **文档与规范**：新增类和函数说明作用、输入、输出及必要性；私有字段使用 `_` 前缀，类和函数采用 PascalCase，普通变量采用 camelCase；规则、实现、测试和操作文档随同一变更保持一致。
