# 京都壹号与场上属性实施计划

> 状态：已按本计划实施完成（2026-10-17），代码、Excel、生成资产与测试均已落地，验证结果见第 14 节。
> 实施记录只说明“做了什么、验证到什么程度”，不构成提交、推送或合并授权。
> 范围依据：用户最终确认的新卡规则，以及“先不开发阶段分类、组牌配额、治疗”的范围约束。

## 1. 目标与范围

添加资源卡“京都壹号”，实现可配置的一次性部署减攻能力，并补齐战斗单位独立于卡种配置的场上战斗属性。

本任务交付范围：

1. 注册京都壹号，默认卡组增加 2 张，支持既有抽牌、部署、墓地洗回流程。
2. 每个具有该能力的在场单位提供一次减攻；多个来源按部署顺序依次触发。
3. 攻击、射程、移动距离、生命上限等战斗属性部署时从只读配置初始化到 `UnitState`；当前生命继续独立保存。
4. 贯通 Excel、校验、SO、Prefab、配置加载、调试配置、规则、快照与表现。
5. 补齐 EditMode、PlayMode 测试及相关文档，使用现有 GitHub Actions PR 检查。

明确不在本任务实现：

- 初级 / 中级 / 后期字段、筛选、组牌配额、选卡界面及阶段解锁。已讨论的阶段归类留给下一任务，本次不落入配置或 UI。
- 治疗、增减生命上限、增减射程等额外技能；本次只准备场上属性存储，不增加这些玩法入口。
- ECS、DOTS、按属性拆分的全局数组、通用技能脚本语言、通用增益到期/驱散系统。
- 新卡专属美术、独立卡种子类或新的第三方依赖。
- 将家改造成普通单位，或改写现有卡牌记录流转机制。

约束来源：[项目规范](../../AGENTS.md)、[游戏内名词](../游戏内名词.md)、[玩法](../玩法.md)。实际实施时先在名词文档登记新增机制，再编写代码。

## 3. 已确认的能力语义

### 3.1 来源单位生命周期

1. 具有该能力的单位成功上场后，立即拥有一次未消耗效果。
2. 召唤失调、已行动不阻止能力触发。能力不占行动次数；若后续配置维持费，沿用被动能力不因欠费自动关闭的处理。
3. 未触发效果跨回合保留；回合开始和产出资源不会补充次数。
4. 来源在触发前因任何原因移出棋盘，其未触发效果随来源一起消失。
5. 触发后来源标记为已消耗，在本次在场期间不能再次触发。
6. 触发后来源离场，不恢复目标单位的攻击力。
7. 同一张卡牌记录再次部署时创建新单位，独立获得新的一次效果；不恢复旧来源的次数。

### 3.2 目标筛选与顺序

一次成功创建战斗单位后，仅当它的 `Category == CardCategory.Attack` 时处理该能力：

- 只考虑同阵营、仍然在场、早于本次目标入场、能力未消耗的来源。
- 按 `DeploymentOrder` 升序选择最早的一个来源；不能依赖集合偶然顺序或 Unity 对象顺序。
- 每次入场最多消耗一个来源的效果，其余来源等待后续目标。
- 无空间/距离要求，作用范围为全棋盘己方单位。
- 有攻击力的资源卡、特殊卡、家都不是目标，也不消耗次数。
- 未来若其他攻击卡配置了同一能力，它不能用本次新获得的效果作用于自己。

所有成功创建攻击单位的现有路径都参与：玩家手牌部署、手动 Boss 部署、AI 首次部署与补兵、刷怪卡生成战机。技能无合法目标而未创建单位时，不消耗效果。

### 3.3 数值结算

对选中的来源和新目标：

```text
目标当前攻击力 = max(0, 目标当前攻击力 - 来源减攻量)
来源能力状态 = 已消耗
```

- 原攻击为 0 时仍消耗一次效果。
- 原攻击为 1、减攻量为 2 时变为 0，仍消耗完整一次效果，不保留“剩余减攻 1”。
- 攻击力为 0 的单位继续遵循现有不能攻击的规则；分类仍为攻击卡，不因数值归零改变分类。
- 减攻持续至目标单位离场；回合切换不重置，来源消失不恢复。
- 本次采用直接更新当前攻击值，不保留负攻击债务，不引入隐藏的负数属性或可撤销修正列表。
- 目标之后再次由同一卡牌记录部署时，从配置重新初始化；是否再次减攻取决于当时是否有可用来源。
- 所有命令合法性校验必须先完成，失败操作不改变来源次数、手牌、墓地、单位或事件。

### 3.4 典型交互

| 场景 | 预期 |
|---|---|
| 京都 A、京都 B 依次上场，再连续部署攻击单位 X、Y | A 影响 X，B 影响 Y；不同时作用于 X |
| A、B 未触发，A 提前离场，再部署 X | B 影响 X |
| 部署京都后，先部署能攻击的资源卡，再部署攻击卡 | 资源卡不受影响、不消耗；攻击卡消耗一次 |
| 已给 X 减攻，移除来源京都 | X 保持减攻 |
| 京都在场数回合后才部署攻击卡 | 仍触发一次；此前产出次数不增加效果次数 |
| 己方通过星门四邻部署攻击卡 | 正常按己方来源顺序触发，星门本身不受影响 |
| 敌方部署攻击卡 | 不消耗我方京都的效果 |
| 攻击为 0 的攻击卡入场 | 消耗一次，攻击仍为 0 |
| 来源被覆盖升级、击杀、主动离场或技能顶替 | 未触发效果消失，不转交新单位 |
| 来源效果已经消耗，但来源继续在场 | 继续按资源规则产出，不再减攻 |

## 4. 配置与场上数据设计

以下类型和字段名称是拟定的实现方案，可在不改变上述语义的前提下按代码规范微调。

### 4.1 继续使用面向对象状态

采用现有 `GameSession` + `UnitState`，不引入 ECS。

- 当前默认棋盘 5 × 10，按回合/命令结算；没有已证实需要按数组批处理的大规模逐帧运算瓶颈。
- 使用属性数组还需要维护单位 ID 到下标、移除压缩、跨数组一致性及快照复制，当前收益不足以抵消复杂度。
- 属性存储方式与规则执行职责分开：单位持有独立数据，`GameSession` 统一执行规则，不让每张卡自行订阅全局事件并修改战局。
- Core 保持 `noEngineReferences: true`。SO 实现只读接口，Core 不引用 `ScriptableObject` 或 `MonoBehaviour`。

### 4.2 三层数据职责

| 层 | 保存内容 | 写入权限 |
|---|---|---|
| 卡种配置：`CardArchetype` / 能力配置 SO | 基础数值、分类、部署限制、能力参数 | Excel 编译发布；对局中只读 |
| 场上状态：`UnitState` | 当前属性、位置、行动状态、能力是否已消耗 | Core 中规则代码 |
| 表现：`Card` / 能力组件 | 配置引用、快照绑定、显示状态 | 不修改权威战斗数据 |

`CardRecord` 仍只保留 ID、卡种 ID 和阵营，不能加入伤势、攻击力或能力次数。

### 4.3 UnitState 字段方案

优先使用值字段，延续现有 `internal set` 风格，避免为了本次能力引入共享可变嵌套对象。

| 字段 | 初始化与用途 |
|---|---|
| `Hp`（已有） | 从配置 `Hp` 初始化，保存当前生命 |
| `MaxHp`（新增） | 从配置 `Hp` 初始化；本次不新增改变上限的玩法 |
| `Attack`（新增） | 从配置 `Attack` 初始化，减攻结算后持久保存 |
| `Range`（新增） | 从配置 `Range` 初始化，所有在场攻击距离判断使用它 |
| `MoveDistance`（新增） | 从配置初始化，所有在场移动范围判断使用它 |
| `DeploymentPenaltyPending`（新增） | 启用能力则初始化为 true；触发后变为 false |
| `DeploymentAttackReduction`（新增） | 从该单位能力配置复制；无能力为 0 |

名称、分类和部署规则继续读取只读卡种配置。资源产出、维持费与传送开关本次仍按既有配置读取，不扩展对应属性修改玩法。

所有创建路径使用同一初始化逻辑，包括 AI 首次部署、补兵和技能生成。新单位不继承旧单位的当前属性或能力状态。

当前 `UnitState.Copy()` 使用 `MemberwiseClone`。新增值字段可以继续保持独立快照；若实现改用嵌套对象或集合，必须同步实现深拷贝，覆盖 `GameSnapshot` 以及领域事件的表现帧，禁止旧快照随后变化。

### 4.4 配置链中的只读性

`CardRow` 是可变的 Excel/调试中间态，不是战斗状态。当前 `GameConfiguration(ConfigDocument)` 的接口可能直接引用行对象，实施时需核对并保证本任务涉及的基础战斗配置和新能力配置在创建对局后不会被外部草稿修改污染；优先在构建运行配置时复制为不可变值。

SO 路径不允许修改资产。测试覆盖“修改原配置草稿不影响已有对局或其后续部署”，避免只保证已上场单位独立、却让后续单位偷偷读取变化后的草稿。

## 5. 能力组件与配置契约

### 5.1 拟定新增类型

| 类型 | 位置 | 职责 |
|---|---|---|
| `IDeploymentPenaltyConfig` | Core 配置契约 | 暴露只读 `AttackReduction` |
| `DeploymentPenaltyConfigSO` | `Runtime/Config/` | 编译生成的能力子资产，实现只读接口 |
| `DeploymentPenaltyComponent` | `Runtime/Cards/` | 持有配置并绑定单位快照，提供减攻量及待触发状态查询 |

在 `CardArchetype` 与 `CardDefinitionSO` 增加可空的能力配置引用；无引用表示不具备该能力。京都壹号组合为 `Card` + `CombatComponent` + `ResourceComponent` + `DeploymentPenaltyComponent`，没有 `TeleportComponent`。

能力为按配置启用的可复用能力，不允许 `if (TypeId == "kyoto_01")` 或按显示名判断。源卡分类不硬编码为资源卡，以支持普通测试夹具和后续卡种复用；目标分类固定使用已确认的 `Category.Attack`。

### 5.2 新字段的校验与兼容策略

拟定的技术约束：

- `deploymentPenaltyComponent` 为布尔字段，默认 false。
- `deploymentAttackReduction` 为非负整数；禁用能力时要求为 0，启用时要求为正整数。
- 京都壹号默认 2 是工作簿数据；其他卡不得隐式获得 2。
- 旧 JSON 缺少两字段时按 false / 0 读取，不自动补卡或改变用户旧卡组数量。
- 新工作簿声明并填写两列；若既有表头校验要求所有声明列存在，旧 Excel 必须显式补列，报错提供迁移提示，不静默重写原文件。
- 旧 SO 的新增能力引用为空，加载保持无能力；正式更新必须按管线重编译并通过门禁。
- 旧配置恢复默认时使用更新后的默认数据，包含京都壹号 2 张。
- 禁用组件时同步清零减攻量；导入矛盾数据应报告错误，不能在校验时悄悄修正用户输入。
- 文档路径、SO 路径和调试路径使用同一业务校验约束，避免绕过其中一个入口。

## 6. 规则实现位置与结算顺序

### 6.1 当前代码事实

- `GameSession.Place` 是现有普通部署、AI 部署及技能生成共用的单位创建入口。
- 当前只有生命等少数属性保存在单位；伤害、攻击范围、移动范围、AI 和刷怪条件仍有直接读取卡种配置的代码。
- 当前所有生成卡种都有战斗组件，因此不能按组件存在性筛选攻击卡。
- `CombatComponent`、`CardText` 等表现入口仍有从基础配置直接显示攻击力的路径。

### 6.2 Place 扩展顺序

1. 调用方完成权限、资源之外的现有部署限制、占位、出牌次数等校验；不新增部署资源费用。
2. 若为合法覆盖或技能顶替，按既有流程移除旧单位及其未触发能力。
3. 从只读配置初始化新 `UnitState`，分配独立 ID 与部署顺序。
4. 若新单位为攻击卡，从本次入场之前已在场的同阵营来源中选择最早的待触发能力。
5. 使用来源实例的减攻量更新新单位攻击，标记来源已消耗；然后完成新单位入场。
6. 保留玩家卡成功部署即进墓地的时机与现有出牌次数结算。
7. 输出部署及减攻事件，调用方取得已经完成减攻的单位；此后才允许 AI 决策和表现帧读取。

可以把步骤 4–5 抽为命名明确的 Core 私有函数，但只从共同创建流程调用一次，不能在玩家命令和 `Place` 各调用一次。

日志至少包含来源单位、目标单位、配置减攻量以及实际攻击前后值；攻击为 0 时也要记录次数已消耗。事件顺序建议为部署事件、减攻事件，快照须表达最终状态。动画仅消费事件，不延迟或回写结算。

### 6.3 必须迁移的场上属性读取点

| 功能 | 应使用的数据 |
|---|---|
| 普通攻击伤害 | 攻击者 `UnitState.Attack` |
| `CanAttack` 与合法目标 | 当前攻击、当前射程 |
| 移动命令和 `GetLegalActions` | 当前移动距离 |
| AI 可击杀优先级 | 当前攻击 |
| AI 待机、寻路、移动截断 | 当前攻击、射程和移动距离 |
| Boss 刷怪卡触发总攻击统计 | 所有玩家在场单位当前攻击之和，继续用 `long` 求和 |
| Boss 前线攻击类数量 | 继续按分类统计；攻击为 0 仍属于攻击卡 |
| 棋盘卡面和单位详情 | 当前生命/上限、当前攻击、射程、移动距离 |
| 手牌、抽牌堆/墓地中的卡牌说明 | 卡种基础配置，不继承场上减攻 |

刷怪条件仍在现有 Boss 回合开始时机读取一次；本任务只改读取数值来源，不改变触发时序。范围外的名称、分类、部署限制与能力定义仍从配置查询。

## 7. 编辑器、资产与表现接入

### 7.1 Excel 与生成资产

修改源数据：`Assets/Spotlight/Config/Spotlight.xlsx`，同步 `DefaultWorkbookWriter` 的 Cards/Deck 默认内容和相关表格说明。更新现有工作簿时保留其余策划调整，不能直接运行“生成默认工作簿”覆盖整个正式文件。

编译器需生成：

- `Generated/Cards/kyoto_01.asset`，包含 Combat、Resource 和新能力子资产。
- `Generated/Cards/kyoto_01.prefab`，仅保存组件组合及 SO 引用，不重复保存数值。
- 更新主配置与编译清单，保留已有资产 GUID。

发布器对新能力支持启用、更新、禁用后移除子资产和组件，以及异常回滚。运行/构建门禁核对组件、配置引用及内容；不能只校验源摘要而漏掉缺失的新组件。

所有 Generated 内容只能经编译管线生成，禁止手工编辑。新增脚本及生成资产应一并带上 Unity `.meta`。

### 7.2 调试配置

在现有逐卡种配置中增加能力开关和减攻量，显示当前配置值；JSON 导出/导入、克隆、“应用并重开”、恢复默认均贯通新字段。

调试界面中的变更只作用于本次运行会话，失败时保留原对局及面板。配置值 2 改为其他合法值后，通过重开生效，不修改已有对局中的单位。

### 7.3 卡面与详情

- 手牌显示基础属性与能力说明；能力数值由配置插入，不写死“减 2”。
- 棋盘卡面、详情与 `CombatComponent` 读取同一单位快照，攻击降为 0 时仍能明确看到 0，不能退回显示基础攻击。
- 来源详情显示“一次性部署减攻：待触发 / 已消耗”，目标详情显示当前攻击，日志可追溯来源。

## 12. 风险与实施注意

1. **读取点遗漏**：只修改伤害会造成 UI、AI 或刷怪条件仍读基础攻击。实施后搜索所有 `Combat.Attack/Range/MoveDistance/Hp` 及可空访问形式，逐项区分配置用途与场上用途。
2. **重复触发**：只在共同创建路径结算，调用方不重复处理；生成失败不能抢先消耗来源。
3. **错误共享状态**：能力待触发状态和当前攻击不得放在 SO、卡种描述或 `CardRecord` 中。
4. **覆写正式配置**：默认生成器只用于同步默认模板；更新现有工作簿保留其他数据和注释。
5. **发布不完整**：新增能力须同时接入发布、删除、回滚与门禁，不能只有运行时代码。
6. **旧资料误导**：旧实现方案中的“只有三个能力组件”和基础属性读取说明需要随实现更新；不得把历史测试通过数当作本次证据。
7. **范围扩张**：生命上限只新增场上字段；治疗、上限变更规则和通用效果到期语义不在本次推导或实现。
